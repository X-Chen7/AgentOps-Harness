# 技术债跟踪

## 1. 使用规则

- 只有明确影响可维护性、稳定性、安全性、性能、交付效率或架构一致性的问题才进入本文件。
- 能在当前任务内安全修复的问题，不进入技术债清单，应直接修复。
- 每条技术债必须有影响描述和建议处理方式。
- P0 和 P1 技术债必须有关联 Owner 或 active 执行计划。
- 关闭技术债时必须说明关闭依据。

## 2. 优先级定义

| 优先级 | 含义 | 处理要求 |
| --- | --- | --- |
| P0 | 已造成严重故障、安全风险或阻断交付 | 立即处理 |
| P1 | 高概率造成线上风险、数据风险或重要交付风险 | 纳入近期计划 |
| P2 | 明显影响维护效率、扩展能力或测试质量 | 排期处理 |
| P3 | 轻微问题或长期优化项 | 定期评估 |

## 3. 状态定义

| 状态 | 含义 |
| --- | --- |
| open | 已登记，尚未排期 |
| planned | 已有处理计划 |
| in_progress | 正在处理 |
| resolved | 已解决 |
| accepted | 明确接受，暂不处理 |

## 4. 分类定义

| 分类 | 说明 |
| --- | --- |
| architecture | 架构边界、模块拆分、依赖方向问题 |
| module-boundary | 模块边界、架构层和业务层职责混乱 |
| sql | 表结构、索引、初始化数据、迁移脚本问题 |
| config | 配置项、profile、环境差异问题 |
| security | 权限、认证、敏感数据、审计问题 |
| test | 单元测试、集成测试、回归验证缺失 |
| documentation | 文档缺失、过期或误导 |
| dependency | 依赖版本、冗余依赖、兼容性问题 |
| runtime | 启动、部署、中间件、运维排查问题 |

## 8. 定期审查规则

- 每个迭代或关键版本前检查 P0/P1。
- 每月检查 open 状态超过一个月的 P2。
- accepted 状态必须写明接受原因。
- resolved 状态必须有关联验证或 completed 记录。
