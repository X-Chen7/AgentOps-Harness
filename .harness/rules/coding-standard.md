# .harness/rules/coding-standard.md

## 1. 文件定位

本文档定义示例后端后端项目的长期编码规范，适用于 Java、Spring Boot、MyBatis-Plus、DO/VO/DTO、异常、事务、日志、枚举、常量和注释等日常开发场景。

本文档只描述长期编码规则，不承载一次性需求方案。注释防遗漏流程见 `.harness/rules/comment-guardrail.md`，交付检查清单见 `.harness/rules/comment-review-checklist.md`。

## 2. Java 基本规范

- 遵循当前模块已有代码风格。
- 不做无关格式化。
- 不批量重排 import。
- 不引入未确认的新工具库。
- 公共方法、DO/VO、复杂业务逻辑必须补充必要中文注释。
- 优先复用项目已有工具类、枚举、错误码和转换器。

## 3. 分层和命名

| 类型 | 规则 |
| --- | --- |
| Controller | 只处理 HTTP 入参、鉴权注解、响应包装和接口协议 |
| Service | 承载业务编排、事务边界和核心校验 |
| Mapper | 只处理数据访问，不写业务编排 |
| DO | 对应数据库表结构 |
| VO | 面向 Controller 请求和响应 |
| DTO | 面向模块间或内部数据传递 |
| Convert | 负责对象转换 |
| Enum | 表达稳定状态、类型、阶段、来源和业务值集合 |

命名要求：

- DO 类以 `DO` 结尾。
- VO 类按 `ReqVO`、`RespVO`、`PageReqVO` 等既有习惯命名。
- Service 接口使用业务能力命名，实现类以 `ServiceImpl` 结尾。
- Mapper 只描述数据访问语义，不命名为业务动作。

## 4. 注释规则

### 4.1 基本要求

- DO 类和字段保持中文注释。
- VO 类和字段保持清晰中文说明，方便前端对接。
- 公共方法说明用途、关键参数、返回语义、关键约束或副作用。
- 注释解释业务原因和边界，不重复代码表面行为。
- 简单 private 方法、getter、setter、纯转发方法不强制注释。

### 4.2 必须写注释的函数

以下函数必须有中文 Javadoc：

- 新增的 `public` / `protected` 方法。
- 业务含义不直观的方法。
- 涉及权限、租户、组织、OAuth2、Token、状态流转的方法。
- 有副作用的方法。
- 复杂条件分支较多的方法。
- 对外部调用方有约束的方法。

### 4.3 函数迭代时的注释维护

函数实现发生以下变化时，必须同步检查并更新注释：

- 方法职责变化。
- 参数语义变化。
- 返回值语义变化。
- 增加前置条件、权限条件、租户条件、组织条件。
- 增加副作用。
- 原有描述已与实现不一致。

代码已修改但注释未同步，视为不合格改动。

### 4.4 推荐格式

```java
/**
 * 校验 OAuth2 授权码并返回对应的客户端和用户上下文。
 *
 * @param code 授权码
 * @param clientId OAuth2 客户端编号
 * @return 授权码对应的业务上下文
 */
```

## 5. 异常和返回

- 优先使用项目已有错误码和异常工具。
- 不直接抛出无语义的 `RuntimeException`。
- Controller 返回结构遵循项目现有 `CommonResult` 风格。
- 不为了绕过错误而吞异常。
- 业务异常应能让调用方明确知道失败原因。

## 6. 事务规则

- 写操作事务边界优先放在 Service 层。
- 不在 Controller 中开启事务。
- 避免在事务中执行耗时外部调用。
- 需要回滚语义时，明确异常类型。
- 事务方法应避免把查询、外部调用和写入混成难以判断的长流程。

## 7. 日志规则

### 7.1 添加日志的原则

日志用于排查和审计，不用于替代业务控制。

应在以下位置考虑加日志：

- 关键业务入口。
- 关键状态流转。
- 外部系统调用前后。
- 异常分支。
- 权限拒绝、租户切换、组织切换、认证失败。
- SQL 或数据修复任务的关键节点。
- 异步任务、消息消费、回调处理。

### 7.2 不应添加日志的情况

- 高频简单循环中无意义打印。
- 敏感信息明文输出。
- 与排查无关的冗余日志。
- 用日志代替异常处理。
- 同一层重复打印同一错误。

### 7.3 日志级别建议

- `info`：关键业务节点、状态变化、重要成功动作。
- `warn`：可恢复异常、非法输入、业务拒绝、预期外但可处理情况。
- `error`：真正失败、需要排查的问题。
- `debug`：仅调试期有价值的信息，不作为生产排查主入口。

### 7.4 敏感信息规则

以下信息不得明文写日志：

- 密码。
- Token。
- 授权码。
- 密钥。
- 完整身份证号、手机号、银行卡号。
- 敏感业务原文。

必要时只打印脱敏值、主键、请求追踪 ID 或摘要。

## 8. MyBatis-Plus 和 SQL

- Mapper 中不写复杂业务编排。
- 查询条件优先保持清晰可读。
- 涉及表结构、初始化数据或修复数据时，DO、Mapper、SQL、文档必须同步。
- 不把 SQL 魔法值散落在业务代码中。
- 复杂 SQL 变更必须遵循 `.harness/rules/sql-and-migration.md`。

## 9. 枚举和常量

- 稳定值集合优先使用枚举。
- 业务魔法值应抽成常量、枚举或配置。
- 不在多个类中复制同一业务字符串。
- 新增枚举值时，需要补充语义说明和必要注释。

### 9.1 什么情况下必须用枚举

以下场景默认必须优先定义枚举，而不是直接写 `private static final Integer/String`：

- 状态值集合，例如启用、停用、草稿、生效、撤销。
- 类型值集合，例如主体类型、资源类型、范围类型、来源类型。
- 有限动作集合，例如隐藏、脱敏、可见、通过、拒绝。
- 会进入 DO 字段、VO 字段、SQL 字段注释、接口协议或前后端约定的稳定值。
- 会进入审计模型、权限判定、资源识别或跨类复用的协议型字符串，例如 `targetType`、主体类型、资源类型。
- 同一取值语义会在多个类之间复用。

如果值集合有明确业务语义、后续可能扩展、需要参与校验或需要在多处复用，视为枚举场景。

### 9.2 什么情况下可以保留常量

以下场景可以保留常量，不强制抽枚举：

- 单个固定协议字符串，例如表字段名、请求头名、权限编码格式模板。
- 不形成有限业务分类的技术参数。
- 仅服务于局部算法的固定阈值、默认值、缓存 key 前缀、正则表达式。
- SQL 字段名、别名、占位模板、日志模板等结构性字面量。

常量如果只是为了替代单个字面量，而不是表达一个“值集合”，不应强行建枚举。

### 9.3 常量注释要求

- 新增 `private static final` 常量默认必须补中文注释，说明它表达的业务或技术语义。
- 字符串模板常量必须说明格式含义和使用场景。
- SQL 字段名、表名、Header 名、缓存前缀等常量，至少说明其对应对象。
- 如果常量承担协议值含义且存在多个候选值，必须改为枚举；只有单个固定模板、字段名、前缀名等非值集合场景才允许保留常量。
- 如果一个常量名不能让不了解上下文的人立刻判断用途，视为必须写注释。
- 多个同类常量成组出现时，不允许只给第一项写总注释而省略其余语义。

### 9.4 禁止写法

- 用一组 `STATUS_1`、`TYPE_2`、`FLAG_3` 一类常量替代本应存在的业务枚举。
- 枚举已存在却在业务代码里重复定义同义常量。
- 新增常量没有注释，导致无法判断其协议含义。
- 把会进入接口、数据库、审计或权限判断的稳定值散落在多个类中重复定义。

## 10. 禁止事项

- 不为通过编译注释业务逻辑。
- 不绕过认证、权限、租户、组织和数据权限。
- 不引入未确认的新依赖。
- 不把框架层问题临时复制到业务模块规避。
- 不把一次性需求说明写入长期编码规则。
