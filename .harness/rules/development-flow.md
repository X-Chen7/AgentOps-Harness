# .harness/rules/development-flow.md

## 1. 文件定位

本文档定义示例后端后端项目的标准开发流程。

目标是统一需求分析、代码阅读、方案确认、实现、验证、Review、交付和文档同步方式，避免直接编码、跳过验证或遗漏文档更新。

本文件适用于后端需求开发、Bug 修复、接口调整、SQL 变更、配置调整、复杂功能迭代和 Harness 文档维护。

## 2. 标准流程

所有任务默认按以下顺序推进：

1. 任务受理。
2. 上下文确认。
3. 影响范围分析。
4. 复杂度分级。
5. 方案判定。
6. 实现前检查。
7. 编码或文档修改。
8. 同步 SQL / 配置 / 对接说明 / Harness 文档。
9. 最小验证。
10. Review 或自检。
11. 交付说明。
12. 文档归档和后续跟踪。

禁止跳过关键步骤直接进入编码或交付。

## 3. 任务受理

收到任务后，先确认任务类型：

- Bug 修复；
- 新增功能；
- 接口调整；
- SQL / 数据修复；
- 配置调整；
- 文档补充；
- 复杂功能迭代。

同时确认任务来源：

- 需求变更；
- 前端联调问题；
- 测试缺陷；
- 线上问题；
- 技术债处理；
- 架构治理。

如果任务目标不清晰，应先明确“要解决什么问题”，再进入实现。

## 4. 上下文确认

开始改动前必须先读上下文，不允许只凭文件路径或类名猜实现。

至少确认以下内容：

- `AGENTS.md`；
- `ARCHITECTURE.md`；
- 目标模块；
- 相关 Controller、Service、Mapper、DO、VO、枚举；
- 相关 SQL；
- 相关配置；
- 相关测试；
- 相关 `.harness/wiki/` 文档。

如果涉及登录、OAuth2、Token、权限、租户、组织、数据权限，必须额外检查对应业务链路和已有实现。

涉及目标业务系统、开放 API、组织用户、业务应用资源、订阅授权、字段权限或 L3 / L4 权限设计时，必须额外执行 `.harness/rules/requirement-alignment-rule.md`。不得只依据当前前端原型、后台页面或已有实现直接确定方案。

## 5. 影响范围分析

开始修改前，必须明确影响范围：

- 涉及哪个模块；
- 是否涉及 `app-framework`；
- 是否涉及 `app-server`；
- 是否涉及 SQL；
- 是否涉及初始化数据；
- 是否涉及接口协议；
- 是否涉及前端联调；
- 是否涉及权限、安全、租户、组织；
- 是否涉及部署或配置变更；
- 是否需要同步 Harness 文档。

如果影响范围跨模块、跨流程或跨角色，不能按“小改动”处理。

## 6. 复杂度分级

所有任务在实现前必须先分级。

| 级别 | 典型场景 | 默认处理方式 |
| --- | --- | --- |
| L1 简单 | 小 Bug、单字段调整、单方法局部修复、纯文档修正 | 可直接进入实现 |
| L2 中等 | 新增接口、接口字段调整、局部 SQL 调整、前后端联调改动 | 先做影响分析，再实现 |
| L3 复杂 | 多接口协作、多状态流转、多表联动、多角色权限判断 | 必须先确认方案，再编码 |
| L4 高风险 | 登录、OAuth2、Token、租户、组织、权限、跨模块改造、破坏性 SQL | 必须先出方案、补设计说明、人工确认后再编码 |

复杂度按最高风险项判定，不按代码行数判定。

## 7. 不同复杂度的处理流程

### 7.1 L1 简单任务

1. 阅读上下文。
2. 确认影响范围。
3. 小范围实现。
4. 执行最小验证。
5. 输出交付说明。

### 7.2 L2 中等任务

1. 阅读上下文。
2. 明确接口、SQL、配置、前端影响。
3. 判断是否需要更新 wiki。
4. 实现。
5. 验证。
6. 更新对接说明或协议说明。
7. 输出交付说明。

### 7.3 L3 复杂任务

1. 使用 `request-analysis` 技能先做需求拆解。
2. 输出影响范围和方案建议。
3. 在 `.harness/changes/active/` 建立执行计划。
4. 在 `.harness/wiki/feature-design/` 补设计说明。
5. 设计说明至少包含流程图、时序图，必要时补状态图。
6. 如果执行计划包含多阶段落地，必须补充详细落地方案。
7. 方案确认后再编码。
8. 分阶段验证。
9. 更新相关 wiki 和 completed 记录。

### 7.4 L4 高风险任务

1. 使用 `request-analysis` 技能做正式分析。
2. 按 `.harness/rules/requirement-alignment-rule.md` 对齐需求章节、系统最终目标、当前代码和复用边界。
3. 明确风险、边界、回滚和联动影响。
4. 建立 active 执行计划。
5. 补功能设计说明。
6. 补详细落地方案，明确模块、表结构、接口、验证、回滚和文档同步要求。
7. 人工确认后才能进入编码。
8. 编码时严格控制改动范围。
9. 完成后进行专项验证。
10. 输出 completed 记录和遗留风险。

## 8. 注释防遗漏流程

所有编码任务都必须执行注释防遗漏判断。

进入编码前，必须确认：

- 是否新增 `public` / `protected` 方法；
- 是否修改已有方法职责、参数语义、返回值语义或副作用；
- 是否新增或调整 DO / VO 字段；
- 是否涉及权限、租户、组织、OAuth2、Token、状态流转。

只要命中任一项，就必须同步执行：

- 更新方法中文 Javadoc；
- 更新 DO / VO 字段中文注释；
- 执行 `.harness/rules/comment-review-checklist.md`；
- 在交付说明中给出注释检查结论。

对于 L3 / L4 任务，active plan 中必须显式包含“补齐或更新方法 / DO / VO 注释”。

## 9. Harness 文档迭代规则

当代码或需求发生以下变化时，必须判断是否同步更新 Harness 文档：

- 业务域模型变化，更新 `.harness/wiki/business-domain.md`。
- 接口协议、Content-Type、请求响应字段、错误码变化，更新 `.harness/wiki/api-contract.md` 和 `.harness/wiki/frontend-integration.md`。
- 表结构、字段语义、初始化数据变化，更新 `.harness/wiki/data-model.md`。
- 启动、profile、中间件、部署方式变化，更新 `.harness/wiki/runtime-and-deployment.md`。
- 复杂功能方案变化，更新 `.harness/wiki/feature-design/`。
- 执行计划变化，更新 `.harness/changes/active/`。
- 任务完成后需要沉淀结果，更新 `.harness/changes/completed/`。
- 发现暂不处理的问题，更新 `.harness/changes/tech-debt-tracker.md`。
- 长期规则变化，更新 `.harness/rules/`，不得只写在聊天记录或一次性交付说明中。

一次性排查记录不写入 `AGENTS.md`。`AGENTS.md` 只维护入口地图和索引。

## 10. 工具和技能使用规则

### 10.1 request-analysis

以下情况必须优先使用：

- L3 / L4 复杂度；
- 需求描述不完整但影响范围大；
- 多模块联动；
- 登录、OAuth2、Token、权限、租户、组织相关任务；
- 需要判断是否先写方案、设计说明或执行计划。
- L4 任务必须判断是否需要单独落地详细实施方案。

### 10.2 coding-skill

进入实现阶段后使用，用于约束最小改动、SQL 同步和最小验证。

### 10.3 expert-reviewer

以下情况建议或必须使用：

- 复杂改动完成后；
- 登录、OAuth2、权限、安全相关改动；
- 准备交付前；
- SQL 变更后。

### 10.4 unit-test-ci

代码完成后执行最小验证时使用。

### 10.5 deploy-verify

涉及启动、装配、profile、依赖或部署前检查时使用。

## 11. 实现前检查

编码前必须完成以下检查：

- 模块已确认启用；
- 目标文件位置正确；
- 已确认可复用现有实现；
- 不会误改未启用模块；
- 不会误改无关业务；
- 是否需要同步文档已经判断；
- 是否需要 Owner 确认已经判断；
- 是否触发注释防遗漏机制已经判断。

如果发现边界不清、职责不清或已有冲突改动，应暂停并先说明问题。

## 12. 编码或文档修改

进入修改阶段时遵循以下原则：

- 优先最小改动；
- 优先复用现有实现；
- 不跨模块复制逻辑；
- 不做无关重构；
- 不做大范围格式化；
- 不批量改名；
- 涉及方法、字段、枚举时同步更新必要中文注释；
- 涉及 SQL 时同步检查 DO、Mapper、VO、初始化数据和文档。

文档任务同样遵循最小改动原则，优先更新正确落点，不把内容写错目录。

## 13. SQL、配置和对接说明同步

如果改动涉及以下内容，必须同步更新。

### 13.1 SQL

- 表结构；
- 索引；
- 初始化数据；
- 修复脚本；
- 字段注释；
- MySQL / KingbaseES 兼容点。

### 13.2 配置

- 新增配置项；
- 修改现有配置项；
- 启动参数；
- Profile 行为；
- 模块装配配置。

### 13.3 对接说明

- 前端接口调用方式变化；
- Content-Type 变化；
- 请求参数变化；
- 响应字段变化；
- 前端可见枚举变化，包括状态、类型、来源、审核结果、访问结果、事件类型、资源类型等；
- 错误码变化；
- 登录、SSO、OAuth2 对接方式变化。

前端可感知的变化必须同步更新：

- `.harness/wiki/frontend-integration.md`
- `.harness/wiki/api-contract.md`

其中枚举字段必须在前端对接说明中显式列出完整取值、中文文案、表单传值规则、列表筛选规则、统计口径和未知值兜底展示方式。不得只在 Java 枚举、DO 字段注释、SQL COMMENT 或 API 协议文档中定义枚举，而遗漏前端对接说明。

## 14. 最小验证

所有任务在交付前必须完成最小验证。

统一验证入口：

```bash
script/check.ps1              # Harness 与快速检查
script/check.ps1 -Backend     # 包含后端模块测试和服务打包
```

默认原则：

- 能局部验证，不做全仓验证；
- 先验证直接受影响模块；
- 再验证启动或装配风险；
- 无法验证时必须说明原因。

验证完成后必须更新 `.harness/PROGRESS.md` 和 `.harness/changes/active/feature-list.json`，不能只把结果写在聊天记录里。

常见验证方式：

```bash
mvn -pl app-module-user -am test
mvn -pl app-module-infra -am test
mvn -pl app-server -am package -DskipTests
```

除命令验证外，还应按任务类型补充：

- 接口调用验证；
- SQL 审查；
- 前后端联调验证；
- 配置生效验证；
- 权限路径验证；
- 注释专项检查。

## 15. Review 或自检

提交交付前必须做 Review 或至少做结构化自检。

至少检查：

- 是否符合模块边界；
- 是否有回归风险；
- 是否遗漏 SQL 同步；
- 是否遗漏配置同步；
- 是否遗漏接口文档更新；
- 是否遗漏前端对接说明；
- 是否遗漏前端可见枚举定义；
- 是否遗漏复杂功能设计说明；
- 是否遗漏注释更新；
- 是否存在未验证范围；
- 是否引入安全风险。

L3 / L4、权限安全、OAuth2、SQL 或跨模块改动，在进入 `ready_for_review` 前必须执行 `expert-reviewer`；验证和评审通过后才能标记完成。

## 16. 交付说明

每次交付至少说明：

- 改了什么；
- 为什么这样改；
- 影响范围；
- 是否涉及 SQL；
- 是否涉及接口变更；
- 是否完成注释检查；
- 是否完成验证；
- 未验证范围；
- 遗留风险；
- 是否同步更新文档。

不允许只说“已修改”或“已处理”。

## 17. 文档归档和后续跟踪

任务结束后，根据任务类型决定是否补归档：

- 同步更新 `.harness/PROGRESS.md` 和 `.harness/changes/active/feature-list.json`；
- 较大任务补 `.harness/changes/completed/`；
- L3 / L4、多阶段、权限安全、跨服务或前后端协作需求完成后，必须新增或维护 `.harness/changes/completed/<中文业务名>需求完成跟踪.md` 需求完成跟踪文档；
- 存在未解决问题时补 `tech-debt-tracker.md`；
- 长期知识补充到 `.harness/wiki/`；
- 复杂功能补充或更新 `feature-design/`；
- 接口变化补充 `frontend-integration.md` 和 `api-contract.md`。

一次性执行过程不要写进 `AGENTS.md` 或 `ARCHITECTURE.md`。

需求完成跟踪文档用于承接“计划完成后的持续维护”，不得只在交付回复中说明。完成跟踪文档至少包含：

- 需求完成结论和完成矩阵；
- 管理端、应用端、测试、运维或跨服务调用方的交付范围；
- 已同步的代码、SQL、接口、原型和 Harness 文档；
- 已执行验证和未验证范围；
- 需求执行过程中形成的关键设计口径；
- 遗留风险、后续行动和需要 Owner 确认的事项。

当后续补充前端原型、接口文档、联调结论、验证结果或设计口径时，必须同步更新对应需求完成跟踪文档，避免 completed 记录停留在一次性归档状态。

## 18. 特殊暂停条件

出现以下情况必须暂停推进并先确认：

- 需要修改 `app-framework`；
- 需要修改根 `pom.xml` 启用关系；
- 需要修改 `app-server/pom.xml` 装配关系；
- 涉及登录、OAuth2、Token、权限、租户、组织核心逻辑变化；
- 涉及删表、删字段、批量数据修复；
- 涉及生产配置、安全配置、密钥策略；
- 与用户已有改动冲突；
- 影响范围明显超出原任务描述。

## 19. 维护规则

以下情况发生时，应同步更新本文档：

- 开发流程变化；
- 验证流程变化；
- 文档体系变化；
- 执行计划和设计说明触发条件变化；
- 模块边界和审批规则变化；
- 注释防遗漏机制变化。

## 20. Git 提交与推送同步

所有改动在标准流程步骤 10（Review 或自检）之后、步骤 11（交付说明）之前完成 Git 状态同步：

1. 更新 `PROGRESS.md` 和 `feature-list.json` 的 status、owner、branch、commit、push_status、pr_url、history。
2. 按 `.harness/rules/git-workflow.md` 的分支和 commit 规范提交，commit message 引用 feature ID。
3. 执行 `script/check.ps1`（涉及后端时 `-Backend`），推送前推荐先运行 `script/sync-changes.ps1 -PushGate`。
4. 推送功能分支并创建 PR/MR；L3/L4、权限安全、OAuth2、SQL 或跨模块改动必须经过 `expert-reviewer`。
5. PR 合入后回写 feature-list 为 `merged`，并在 completed 记录和 `completed/INDEX.md` 中补充 commit、PR 和仓库信息。

当前目录不是 Git 仓库时，按 `.harness/rules/git-workflow.md` 第 6 节降级处理，不得伪造 commit 信息。
