# .harness/rules/comment-guardrail.md

## 1. 文件定位

本文档定义后端开发中的“注释防遗漏机制”。

目标不是补充一条建议，而是把注释要求变成可执行的开发约束、流程卡点和交付检查项，避免后续出现“功能完成但注释缺失”或“实现已变更但注释未更新”的情况。

## 2. 适用范围

以下改动默认受本机制约束：

- 新增 `public` / `protected` 方法；
- 修改已有 `public` / `protected` 方法；
- 涉及权限、租户、OAuth2、Token、状态流转、组织绑定、审计的业务方法；
- 新增或修改 DO / VO 字段；
- 多文件联动或复杂逻辑迭代任务。

## 3. 强制规则

### 3.1 开发前规则

- 开始编码前，必须判断本次改动是否触发注释补充或更新。
- 新增 `public` / `protected` 方法，默认必须编写中文 Javadoc。
- 修改已有方法的职责、参数语义、返回值语义、副作用、权限条件、租户条件、组织条件时，默认必须检查旧注释是否失效。
- 新增或调整 DO / VO 字段时，默认必须同步补充或更新字段中文注释。
- 新增 `private static final` 常量时，默认必须同步补充中文注释，并判断是否应升级为枚举。

### 3.2 编码中规则

- 注释未补齐的代码，不视为完成。
- 涉及高风险业务的方法，注释必须说明方法用途、关键约束、返回语义和副作用。
- 注释应解释业务原因、边界和约束，不重复描述代码字面动作。
- 简单 getter、setter、纯转发且语义清晰的方法不强制单独添加注释。
- 一组稳定业务取值若使用常量表达，必须先证明不适合建枚举；否则视为不合规设计。

### 3.3 迭代中规则

如果方法实现发生以下变化，必须同步更新注释：

- 方法职责变化；
- 参数含义变化；
- 返回值语义变化；
- 新增权限判断；
- 新增租户判断；
- 新增组织判断；
- 新增副作用；
- 注释与实现不再一致。

## 4. 流程卡点

### 4.1 任务受理阶段

- 如果任务包含新增接口、新增服务方法、新增 DO / VO 字段，默认把“同步处理注释”纳入任务范围。
- 如果任务属于权限、租户、OAuth2、Token、状态流转、组织绑定等领域，默认标记为注释重点检查任务。

### 4.2 实现前检查阶段

进入编码前，必须明确回答：

- 本次是否会新增 `public` / `protected` 方法；
- 本次是否会修改已有方法职责；
- 本次是否会新增或调整 DO / VO 字段；
- 本次是否会改变副作用、权限条件、租户条件、组织条件或返回语义。

只要任一答案为“会”，就必须把“同步更新注释”列入当前任务，不得后置。

### 4.3 编码阶段

- 新增方法时，优先在方法声明前先写 Javadoc，再写实现。
- 修改方法实现时，同时检查原注释是否仍然成立。
- 修改 DO / VO 字段时，同时检查字段中文注释是否完整、准确。

### 4.4 执行计划阶段

对于 L3 / L4 或多文件任务，active plan 中必须显式加入：

- 补齐或更新方法 / DO / VO 注释。

未写入该项，视为计划不完整。

### 4.5 Review / 自检阶段

提交前必须执行注释专项检查，至少包括：

- 新增 `public` / `protected` 方法前是否存在 Javadoc；
- 修改过的方法，注释是否仍与实现一致；
- 新增 DO / VO 字段是否有中文注释；
- 是否存在“功能完成但注释未补”的遗漏。

## 6. 交付判定

满足以下任一情况，当前改动不得视为完成：

- 新增 `public` / `protected` 方法无中文 Javadoc；
- 方法职责已改但注释未更新；
- DO / VO 新增字段无中文说明；
- 注释与实现明显不一致；
- 明显属于高风险业务方法但无关键约束说明。
